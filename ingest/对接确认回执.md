## 1. 三处纠偏（你方 spec 对我库的假设）

### 1.1 不需要 ALTER 大表加那 5 个字段
`meta_json` 是 `jsonb`（schemaless）。`nameHists / capitalHists / jpNationCharts / basicFinCharts / extSecLic / _patch_meta` **写入即生效，无需任何 DDL**。你方 spec §3、§7.4 关于"生产库要允许保存新增字段"的动作**我方无需做**，194 万行大表零迁移风险。

### 1.2 不需要新建 spec §4 的 jpno 函数索引
我库里 **`slug` 恒等于 `meta_json->>'jpno'`**，且 `(site_id, content_model_id, slug)` **已是唯一索引**（约束名 `cms_content_entries_site_id_content_model_id_slug_key`）。manifest / upsert / patch 全部走这个现成唯一键，毫秒级、天然幂等。spec §4 的 `idx_..._jpno` 与 `idx_tce_has_patch_meta` **均不新建**。

> 对你方无影响：你方仍按 `jpno` 作唯一键推送即可，我方内部用 `slug=jpno` 定位。

### 1.3 "不覆盖浏览量/搜索量"自动满足
我方的浏览量/搜索点击量**本就不在 meta_json**，而在独立表 `thaicompany_views` / `thaicompany_search_hits`。upsert/patch 只碰 `meta_json`，**绝不会**动到行为数据。spec §2.3、§5.4 的这条约束我方结构上就保证了。

## 2. 已实现的接口（路径/语义与 spec 对齐）

base：`https://bizthai.com/api/internal/dbd`（仅对你方出口 IP 开放，见 §4）

| 接口 | 方法 | 说明 |
|---|---|---|
| `/thaicompany/manifest/query` | POST | 批量比对，返回 exists/entry_id/source_update_date/content_hash/updated_at |
| `/thaicompany/upsert-batch` | POST | 完整企业 upsert（`mode=upsert_if_newer`） |
| `/thaicompany/patch-fields-batch` | POST | 5 字段合并（`mode=merge_patch_fields`）—— 126M 补采主力 |
| `/sync/batches/{batch_id}` | GET | 批次核对 |
| `/health` | GET | 健康（不鉴权，仅回 ok + db ping） |

请求/响应体**与你方 spec §2 一致**。差异/补充见下。

### 2.1 upsert-batch 行为（服务端判定）
```
不存在                                        → INSERT（并自动关联 province/companytype 分类）→ inserted
incoming.source_update_date > 库内 updatedate → UPDATE 全量 meta_json                          → updated
日期相同 且 incoming.content_hash != 库内 hash → 默认进 review 不写                              → conflict_same_date_changed
否则                                          → skip                                          → skipped_not_newer
```
- **瘦接收**：你方送来的 `entry.meta_json` 是**成品**（含 profile/raw/i18n 三语 + 5 字段），我方原样落库。三语/中文字段的注入（原 `mapping.display_meta`）由你方管线负责——新公司若缺 `i18n`/`xxxzh` 字段，前台会退英/泰兜底。
- 新公司入库后会关联 `province`(`meta.province`) 与 `companytype`(`meta.jptypedesc`) 两个 term；这两个键请保持在 meta_json 内（你方 mapping 已产出）。
- 新公司进入**列表/analytics 统计**需等我方 `thaicompany_facts` 物化视图刷新（日级）；**详情页立即可见**。补采字段只在详情页读，不受此影响。

### 2.2 patch-fields-batch 行为
```sql
UPDATE ... SET meta_json = meta_json || :patch::jsonb WHERE slug = :jpno
```
- `:patch` = **仅你方传入的字段**（缺失字段不动；`[]`/`{}` 照写，表示源站确认无数据）+ `_patch_meta`。
- 顶层浅合并自动保留 `profile / raw / i18n / _sync` 等一切未传字段。
- 命中 0 行 → `missing_company`。天然幂等。
- `_patch_meta` 由我方写入（记录 patch_source / patch_batch_id / patch_collected_at / jpTypeCode / patch_fields_version）。

## 3. 需你方确认/遵守的契约点

### 3.1 content_hash 约定
- **manifest 回读的 `content_hash` 来源 = 上一次 upsert 时你方随 `entry` 送来的 `content_hash`**（我方存到 `meta_json._sync.content_hash`）。
- **patch 不改 content_hash**（补采包本就不带 hash；且 hash 代表"完整企业内容"，补采是补充字段）。
- **存量老公司在首次被你方 upsert 之前，manifest 的 `content_hash` 返回 `null`**（老 dump 没有这个字段）。你方比对逻辑请把 `null` 视为"未知，按 source_update_date 判定"。
- 请你方固定 hash 算法口径（我方只存不算），建议 sha256(规范化后的关键内容)。

### 3.2 冲突策略（日期相同、内容不同）
- 默认 `review`：**不写**，返回 `conflict_same_date_changed`，计入批次 `conflict_count`。
- 如需改为直接覆盖，可切 `overwrite`（我方配置项，一句话切换）。请你方确认默认走 review 是否 OK。

### 3.3 幂等与重试
- 幂等键 = `batch_id`（也接受请求头 `Idempotency-Key`，二者一致）。
- **批次一旦 `completed` 即终态**：重放同 `batch_id` 直接回放已存计数，**不重复写**。
- **若批次里有 `failed` 条目要重试，请用新的 `batch_id` 重推这些条目**（不要复用已 completed 的 batch_id，否则只会拿到回放结果）。

### 3.4 批量与体积上限
- 单批条数：默认上限 **2000**（可配 500~2000）。超限返回 `400 batch_too_large`。
- 单请求体：默认上限 **64MB/批**。超限返回 `413 payload_too_large`。
- manifest 单次 jpno：默认上限 **5000**。

### 3.5 dry-run
- 支持 `?dry_run=true` 或请求体 `dry_run:true`：只返回 insert/update/skip/patch/missing 的分类统计，**不落库、不写日志表、不需要 batch_id**。

### 3.6 jpno 口径
- jpno 视作 slug，允许 `[A-Za-z0-9-]{1,64}`。非法 jpno 计入 `failed` 并在 `errors[]` 返回，不阻塞整批。
